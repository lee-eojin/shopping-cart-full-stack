> 스펙과 이 프로젝트의 구현 결정을 함께 정리한다. 테스트 범위(§4)는 PR에 그대로 옮겨
> 선정 이유로 쓴다.
>

> - 〔확정〕 미션 스펙에 명시된 사실

## 0. 미션이 요구하는 것

학습 목표 〔확정〕:
- 구현에 의존하지 않는 인터페이스를 설계한다.
- 안정적인 소프트웨어를 위해 테스트 범위를 스스로 정의한다.
- 서버 응답과 클라이언트 상태의 책임을 명확히 나누어 관리한다.

구현 범위 〔확정〕: 3단계 요구사항과 설계도에 맞게 구현한다. 새 기능을 추가하는 단계가
아니라, 3단계에서 확정한 계약과 계산 규칙을 동작하는 코드로 옮기는 단계다.

배포와 DB:
- Railway로 배포한다. 〔확정〕
- in-memory DB를 supabase로 교체한다. 〔선택〕

## 1. 전체 프로그래밍 요구사항

### 1.1 테스트 〔확정〕

안정적인 소프트웨어를 위해 자동화 테스트 범위(E2E, 단위, 통합)와 대상을 스스로 정의하고
테스트한다. 대상 선정 이유를 PR에 남긴다. → 범위와 근거는 §4.

### 1.2 인터페이스 〔확정〕

함수와 클래스의 인터페이스는 복잡한 구현을 숨긴다. 호출부에서 알 필요 없는 것은 매개변수로
받지 않고, 내부 구조를 알아야만 이해되는 매개변수를 조심한다.

이 프로젝트에 적용:
- 계약은 능력만 노출하고 전략은 숨긴다. `secondPrice`(전 조합 전수계산 결과)를 계약에서
  걷어내고, 예상 할인은 선택 조합을 묻는 `GET /order/coupons/preview`로 바꿨다(STEP3 스펙
  §5.1, `api.md`). 호출부는 "이 선택의 할인은 얼마인가"만 알면 되고, 서버가 전 조합을
  미리 계산하는지는 알 필요가 없다.
- `PATCH /order/coupons`는 적용 쿠폰만 받는다. 주문 항목과 도서산간은 서버가 주문서로
  보유하므로 다시 받지 않는다. 호출부가 몰라도 되는 것을 매개변수에서 뺐다.
- FE의 `couponRules` 의존은 없다. 금액 계산은 BE 안에 숨고, FE는 식별자와 플래그만 보낸다.

### 1.3 라이브러리

- 스타일링: emotion으로 통일한다. 〔확정〕 쿠폰 `applicable` 비활성화, 버튼 variant 등
  상태별 스타일 분기가 많아 prop 기반 동적 스타일이 컴포넌트 추상화(§2.1)와 잘 맞는다.
- 페이지 전환에 react-router 사용 가능(필수 아님).
- 이전에 학습한 것(msw, storybook)과 명시된 라이브러리 외에는 직접 구현한다. 〔확정〕

## 2. FE 프로그래밍 요구사항

### 2.1 컴포넌트 추상화 〔확정 요구 / 해석〕

비슷하지만 다른 UI를 구현할 때 추상화 여부를 결정하고 근거를 남긴다.

이 프로젝트의 판단 대상 〔해석〕:
- 쿠폰 카드(`CouponItem`): 종류마다 표시 정보가 다르지만(정액/정률/무료배송/BOGO) 카드의
  뼈대와 `applicable` 비활성화 처리는 공통이다. 공통 뼈대는 추상화하고 종류별 표시는
  분기한다.
- 금액 4행(주문 금액, 할인, 배송비, 총액): 같은 라벨 더하기 금액 행이라 한 컴포넌트로
  추상화한다.
- 버튼: "쿠폰 적용", "사용하기", "결제하기"는 라벨과 동작만 다르므로 공통 버튼에 props로
  주입한다.
- 추상화하지 않을 것: 주문 확인 화면과 결제 확인 화면은 표시 데이터와 목적이 달라 억지로
  합치지 않는다.

### 2.2 상태 관리 〔확정〕

서버 상태를 하나의 원천 상태(SSOT)로 관리하고, 서버 응답과 클라이언트 상태의 책임을
나눈다(STEP3_REQUIREMENTS §3.11, §3.13).

- 서버 상태(SSOT): 주문서(항목, 적용 쿠폰, 도서산간, 금액 4종), 쿠폰 판정. 자체 쿼리 캐시
  레이어(`shared/api/query`의 `useQuery`/`queryCache`)로 관리한다. `GET /order/coupons/preview`도
  선택 조합을 키로 한 쿼리로 두어, 이전 조합으로 되돌아갈 때 캐시를 재사용한다.
- 클라이언트 상태: 모달 안 임시 선택(컴포넌트 로컬, 확정 전 폐기), 선택 여부(localStorage,
  step 2).
- 금액 4종은 FE가 만들지 않는다. 항상 서버 응답을 표시한다.

## 3. BE 프로그래밍 요구사항

### 3.1 구현 〔확정〕

설계에 시간을 과하게 쓰지 않고 단일 책임 기반 구현에 집중한다. 안정적으로 도는 코드를
만들고 FE 구현에 집중한다.

- 엔드포인트(`api.md`): `POST /order`, `GET /order`, `PATCH /order/coupons`,
  `GET /order/coupons/preview`, `PATCH /order/destination`, `GET /coupons`.
- 도메인 규칙은 `couponRules` 순수 함수에 모은다(STEP3 스펙 §3): `assessCoupon`,
  `calcComboDiscount`, `pickBestCombination`, `calcAmounts`.

### 3.2 배포 〔확정〕

Railway로 배포한다.

### 3.3 DB 〔선택〕

in-memory DB를 supabase로 교체한다. 교체하더라도 `couponRules`는 DB를 모르는 순수 함수로
유지해, 저장소 변경이 도메인 규칙에 새지 않게 한다.

## 4. 테스트 범위 (스스로 정의) — PR 기록용

무게중심을 단위 테스트에 둔다. 금액을 결정하는 분기가 `couponRules`에 모여 있어, 같은
규칙을 적은 비용으로 가장 촘촘히 검증할 수 있기 때문이다. 통합은 계약(엔드포인트 입출력)을,
E2E는 핵심 사용자 흐름만 얇게 덮는다.

### 4.1 단위 — couponRules 순수 함수 (가장 두껍게)

STEP3_REQUIREMENTS §5의 케이스 대부분이 여기로 온다.
- `assessCoupon`: 만료 경계, 시간대 경계, 최소 주문 금액, BOGO 대상 상품 포함 여부와 수량.
- `calcComboDiscount`: 정액 먼저 그리고 정률은 할인된 금액에, 정률 상한 적용, 원 미만 절사,
  FREESHIPPING이 정률 기준 금액을 줄이지 않음.
- `pickBestCombination`: 2장 이하 전수 평가의 최대값(개별 상위 2개 합산 아님).
- `calcAmounts`: 배송비 경계(99,999 / 100,000, 도서산간), 총액 최저 0원.

### 4.2 통합 — 라우트와 계산 결합

- `PATCH /order/coupons`: 적용 쿠폰 저장과 재계산 응답, 3장 이상/중복/적용 불가 거부.
- `GET /order/coupons/preview`: 저장하지 않고 예상 할인만 반환, preview 값과 이후 확정(PATCH)
  응답 금액의 일치.
- `PATCH /order/destination`: 도서산간 갱신과 배송비 재계산.
- `GET /coupons`: applicable 판정과 primaryPrice.

### 4.3 E2E — 핵심 사용자 흐름

- 주문 확인 진입(최적 조합 자동 적용 표시) → 모달에서 쿠폰 토글(버튼 총 할인액 갱신) →
  "사용하기" → 금액 4종 갱신 → 결제 확인 화면 전환.
- 도서산간 토글 시 재계산. 새로고침과 직접 URL 접근 시 서버 상태로 복원.

### 4.4 우선순위 낮음 / 비대상

- step 2 장바구니 합계 표시(쿠폰 미개입 파생값).
- 단순 표시 전용 컴포넌트의 스냅샷.

## 5. 이번 단계가 들고 가는 설계 결정 (STEP3에서 확정/확장)

- 예상 할인은 `GET /order/coupons/preview`로 얻는다. GET 선정 이유는 `api.md`에 문단으로
  기록(부수효과 없는 읽기, idempotent, 캐시 재사용, 미리보기와 확정의 책임 분리).
- 〔확장〕 BOGO 적용 대상 한정(`applicableProductIds`)과 정률 상한(`maximumDiscountAmount`
  = 100,000). 스펙의 〔확정〕 정의에서 벗어나는 현실성 보강이므로 PR에서도 확장으로 밝힌다.
- `secondPrice` 제거. 계약은 능력만 노출하고 전 조합 전수계산 전략은 숨긴다.
