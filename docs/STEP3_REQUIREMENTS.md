# Step 3 요구사항 문서 — 쿠폰과 배송비 정책

> 구현 전에 요구사항 해석과 모호한 부분을 확정하는 문서. 실제 미션 스펙(2026 레벨2
> 장바구니 3단계) 공개에 맞춰 갱신했다. 가정 기반 초안에서 바뀐 해석은 본문에 "개정"으로
> 표시한다.
>
> 표기 규칙
> - 〔확정〕 미션 스펙에 명시된 사실
> - 〔해석〕 스펙이 모호해서 이 문서에서 근거를 들어 결정한 해석
> - 〔확장〕 스펙에 없으나 현실성을 위해 더한 정책. 스펙의 〔확정〕에서 벗어날 수 있어 따로 표기한다

---

## 0. 미션이 요구하는 것

학습 목표 〔확정〕:
- 요구사항을 해석하여 안정적인 소프트웨어를 만들기 위한 FE-BE 책임 경계를 설계할 수 있다.
- 쿠폰 도메인을 API로 설계하고, 그 선택을 설명할 수 있다.

설계 산출물 〔확정〕:

| 산출물 | 내용 | 위치 |
| --- | --- | --- |
| 요구사항 문서 | 요구사항 해석과 모호점 확정 | 이 문서 |
| 시스템 설계 | 시퀀스 다이어그램(Frontend, Backend, DB) + SSOT 설계 | `docs/system-design.md` |
| API 명세 | 쿠폰 도메인 API + 선택 근거 | `docs/api.md` |

시스템 제약 〔확정: 스펙 명시〕:
- 쿠폰을 적용하고 결제 금액을 확인하는 과정에서 클라이언트가 임의로 계산하지 않도록
  설계한다. SSOT(Single Source of Truth)를 어디로 둘 것인가 고민해서 설계한다.
- 상품 정보, 수량, 선택 여부, 쿠폰 등 핵심 상태는 하나의 원천 상태로 관리한다.
- 쿠폰 등록, 수정, 삭제 API는 구현하지 않는다. 쿠폰 데이터는 DB에 하드코딩.
- 결제 API는 구현하지 않는다.

4단계 예고 〔확정〕: 이 설계를 바탕으로 FE-BE 통합, 경계값과 복합 조건은 테스트로 명세.
이 문서의 §5가 4단계의 입력이 된다.

## 1. 용어 정의

| 용어 | 코드 이름 | 정의 |
| --- | --- | --- |
| 주문 금액 | `orderAmount` | 선택된 상품의 `price × quantity` 합. 쿠폰 적용 전 금액 |
| 쿠폰 할인 금액 | `couponDiscount` | 적용된 쿠폰 조합의 총 할인액 |
| 배송비 | `shippingFee` | 기본 배송비 + 도서산간 추가비 |
| 최종 결제 금액 | `total` | `orderAmount − couponDiscount + shippingFee` (최저 0원, §3.8) |
| 원천 상태 (SSOT) | — | 각 상태의 유일한 진실 출처. 같은 정보를 두 곳이 소유하지 않는다 |

- 〔확정〕 스펙이 화면에 표시하라고 명시한 금액이 위 4종이다("주문 금액, 할인 금액, 배송비,
  최종 결제 금액").
- 〔해석〕 무료 배송 쿠폰의 할인은 배송비를 0으로 만드는 게 아니라 `couponDiscount`에
  배송비만큼 더하는 방식으로 표현한다. 금액 4행의 구조가 쿠폰 종류와 무관하게 일정해진다.

## 2. 도메인 요구사항

### 2.1 쿠폰 4종 〔확정〕

| 코드 | 종류 | 할인 | 적용 조건 | 만료일 |
| --- | --- | --- | --- | --- |
| `FIXED5000` | 고정 할인 | 5,000원 | 최소 주문 금액 100,000원 | 2026-11-30 |
| `BOGO` | 2+1 | 단가 가장 높은 대상 상품 1개 무료 | 동일 상품 2개 구매 시 1개 무료 (§3.4) | 2026-06-30 |
| `FREESHIPPING` | 무료 배송 | 배송비 전액 (도서산간 추가비 포함) | 최소 주문 금액 50,000원 | 2026-08-31 |
| `MIRACLESALE` | 시간제 퍼센트 | 30% | 오전 4시 ~ 7시에만 적용 | 2026-07-31 |

〔확장〕 스펙 외 현실성 보강 (이번 설계에서 추가):
- BOGO 적용 대상 한정: 2+1이 모든 상품에 보편 적용되는 것은 비현실적이라(맥북 2+1 등),
  BOGO 쿠폰에 `applicableProductIds`를 두어 적용 대상 상품을 한정한다. 적용 판정은 대상
  상품이 장바구니에 buyQuantity 이상 담겼는지를 본다. 무료 수량은 대상 상품에서 나온다.
  스펙의 〔확정〕 BOGO 정의(장바구니 전체에서 단가 최고 상품)에서 벗어나는 확장이다.
- 정률 할인 상한: 큰 주문에서 정률 할인이 과도해지므로(1,000,000원 주문에 300,000원 등),
  MIRACLESALE에 `maximumDiscountAmount`(100,000)를 둔다. 정률 할인액은 min(정률 적용액,
  상한)으로 계산하고 상한은 정률 부분에만 건다. 스펙의 30% 정의에 상한은 없으므로 확장이다.
- fixed와 freeShipping은 장바구니 전체 적용을 유지한다(스코프가 꼭 필요한 것은 BOGO뿐).
- issuer(발행 주체)는 표시가 필요할 때만 메타로 추가하고 계산 분기에는 쓰지 않는다.

### 2.2 쿠폰 복합 적용 〔확정: 스펙 보강 공지〕

- 최대 2개 쿠폰을 동시에 사용할 수 있다.
- 가장 할인 효과가 큰 조합이 먼저 계산되어서 적용되어야 한다.
- 정액 쿠폰(FIXED5000, BOGO, …)을 먼저 적용하고, 할인된 금액에서 정률 쿠폰
  (MIRACLESALE, …)을 적용하여 최종 금액을 계산한다.
  - 초기 스펙에서 모호했던 두 지점(자동 적용 여부, 정률의 기준 금액)이 보강 공지로
    확정됐다. 해석 변경의 연쇄는 §3.1, §3.3, §3.12 참고.

### 2.3 배송비 정책 〔확정〕

- 쿠폰 적용 후 결제 금액과 무관하게, 주문 금액(쿠폰 적용 전) 100,000원 이상이면 무료 배송.
- 제주도 및 도서산간 지역 선택 시 배송비 3,000원 추가.
- `FREESHIPPING` 쿠폰은 도서산간 추가 배송비까지 무료 처리.
- 〔해석/개정〕 10만원 이상 무료 배송은 도서산간 추가비까지 포함한 전액 면제다.
  - 근거: "무료 배송"은 사용자 입장에서 배송비 0원이라는 안내다. 추가비만 남기면 화면에
    "무료 배송" 문구와 배송비 3,000원이 동시에 떠 안내와 어긋난다.
  - 귀결: `shippingFee = 주문 금액 ≥ 100,000 ? 0 : 3,000 + (도서산간 ? 3,000 : 0)`
  - 〔개정 이력〕 초안은 "추가비는 별도 부과"로 해석했으나 전액 면제로 확정.
- 주문 금액 0원(선택 상품 없음)이면 배송비 0원. 〔해석: step 2 규칙 유지〕

### 2.4 화면 요구사항 〔확정〕

주문 확인 페이지 (`/order`, 기존 페이지 확장)
- 사용자가 최대 2개의 쿠폰을 선택할 수 있는 UI(쿠폰 모달)를 제공한다.
- "제주도 및 도서산간 지역" 체크박스를 제공한다.
- 선택한 쿠폰과 장바구니 정보를 바탕으로 주문 금액, 할인 금액, 배송비, 최종 결제 금액을
  표시한다. 이 값들은 서버 응답이다(§3.11).
- 〔해석: 기존 step 2 규칙 유지〕 새로고침과 직접 URL 접근에도 안전 (서버 상태 재조회,
  `location.state` 의존 금지). 상세 UI는 Figma 참조.

쿠폰 모달
- 사용 가능한 쿠폰 목록을 표시한다. 〔확정〕
- 적용할 수 없는 쿠폰은 비활성화한다. (서버 판정 결과를 표시, §3.11)
- 쿠폰별 할인 금액과 선택 시 총 할인액을 표시한다. (선택 시 총 할인액은 `GET /order/coupons/preview` 응답, §3.12)
- 〔해석〕 모달 안의 선택은 임시 상태다. "사용하기"로 확정, 닫으면 폐기. (Figma의 확정
  버튼 존재가 근거)

결제 확인 페이지 (신규)
- 〔확정〕 결제 API는 구현하지 않는다. "결제하기"는 이 화면으로의 전환까지만.
- 주문한 상품 종류 수와 총 수량, 총 결제 금액(서버가 계산한 값)을 표시한다. (Figma)
- "장바구니로 돌아가기" 버튼이 있다.
- 〔해석〕 이 화면도 `GET /order`로 그린다. 별도 데이터 전달(`location.state`) 없이
  새로고침에도 안전. 종류 수와 수량 세기는 금액 계산이 아닌 표시용 집계라 클라 계산
  허용(§3.11).

### 2.5 상태 설계 요구사항 〔확정〕

- 상품 정보, 수량, 선택 여부, 쿠폰 등 핵심 상태는 SSOT로 관리한다.
- 결제 금액, 할인 금액, 배송비 등 계산 결과를 서버와 클라이언트 중 어디서 관리할지
  설계한다. → 결정: 서버 (§3.11, `system-design.md`)

## 3. 요구사항 해석 — 모호점과 결정

### 3.1 할인 계산 규칙 〔확정〕 → 정액 먼저, 정률은 할인된 금액에 〔스펙 보강으로 재개정〕

스펙 보강 공지로 모호점이 해소됐다: 정액 쿠폰을 먼저 적용하고, 할인된 금액에서 정률
쿠폰을 적용한다.

- 계산식: `couponDiscount = 정액 할인 합 + ⌊(orderAmount − 상품 정액 할인 합) × rate/100⌋`
- 예: 주문 100,000원에 FIXED5000 + MIRACLESALE
  → 5,000 + (100,000 − 5,000) × 30% = 5,000 + 28,500 = 33,500원
- 〔해석〕 남는 해석: "할인된 금액"은 상품 금액 차원으로 본다. FREESHIPPING은 배송비를
  깎는 정액 쿠폰이므로 정률의 기준 금액(상품 금액)을 줄이지 않는다.
- 귀결: 쿠폰 할인이 서로 상호작용하므로 최적 조합을 "개별 할인액 상위 2개"로 구할 수
  없다. 2장 이하 조합(최대 10개)을 전수 평가한다. 적용 순서는 규칙이 고정하므로
  (정액→정률) 순서쌍 탐색까지는 불필요.
- 〔개정 이력〕 순차 적용(작년 문구 근거) → 독립 적용(올해 초기 스펙의 문구 삭제) →
  정액 선적용, 정률 후적용(보강 공지). 두 번 뒤집힌 항목이다. 모호점을 해석으로 격리해둔
  덕에 변경이 이 문서와 계산 모듈 안에서 끝난다.

### 3.2 쿠폰 적용 조건의 기준 금액 〔해석〕 → 항상 원 주문 금액 기준

정액 할인이 먼저 적용되어 금액이 내려가더라도, 최소 주문 금액 조건(`FIXED5000`,
`FREESHIPPING`)의 판정은 항상 할인 전 `orderAmount` 기준이다. 근거: "10만원 이상 구매
시"는 담은 금액에 대한 조건이고, 다른 쿠폰을 썼다고 자격이 사라지는 건 직관에 반한다.
배송비 무료 기준이 "쿠폰 적용 전 금액"으로 명시된 것(§2.3)과 같은 계열의 규칙.

### 3.3 최적 조합의 제공 방식 → 주문서 생성 시 서버가 자동 적용 〔확정〕, 이후 사용자 소유 〔해석/개정〕

- 자동 적용은 이제 해석이 아니라 스펙이다. 보강 공지: "가장 할인 효과가 큰 조합이
  먼저 계산되어서 적용되어야 한다." 주문서 제출(`POST /order`) 시점에 서버가 계산해서
  이미 적용된 채로 응답한다(계산 SSOT, §3.11). 사용자는 진입하자마자 가장 유리한
  금액을 본다.
- 〔해석〕 이후에는 사용자 소유로 해석한다. 사용자가 모달에서 바꾼 선택(`PATCH /order/coupons`)을
  시스템이 덮어쓰지 않는다. "먼저 계산되어 적용"과 "사용자가 선택할 수 있는 UI"가
  공존하려면, 자동은 초기값이고 이후는 사용자 선택이어야 한다.
- 컨텍스트 변화(도서산간 토글 등)로 적용 중 쿠폰이 무효가 되면 서버가 그 쿠폰만 해제하고
  재최적화하지 않는다.

### 3.4 BOGO의 적용 범위 〔해석〕 → 대상 1개 상품, 무료 1개만

- 〔확정〕 명시: 동일 상품 2개 구매 시 1개 무료, 단가 가장 높은 상품에 적용.
- 〔해석〕 "2개 구매 시 1개 무료"의 조건은 같은 상품이 3개 이상 담겨 있을 때(구매 2 +
  무료 1)로 해석한다. 할인액 = 대상 상품의 단가 × 1.
- 〔해석〕 같은 상품을 6개 담아도 무료는 1개다. 쿠폰 1장 = 혜택 1회.

### 3.5 만료일 경계 〔해석〕 → 만료일 당일은 유효

만료일 2026-06-30이면 6월 30일 23:59:59까지 유효, 7월 1일 00:00:00부터 불가.
판정 시계는 서버다(§3.10).

### 3.6 시간제 쿠폰의 경계 〔해석〕 → 양끝 포함

오전 4시~7시 → `04:00:00 ≤ now ≤ 07:00:00`. 04:00:00 정각과 07:00:00 정각 모두 적용
가능, 07:00:01부터 불가.

### 3.7 퍼센트 할인의 소수점 처리 〔해석〕 → 원 단위 절사(내림)

30% 할인 시 소수점이 생길 수 있다(예: 35,555원 × 30% = 10,666.5원). 원 단위 미만
절사로 정의한다. 할인은 판매자 부담이므로 보수적으로 잡는다. 계산 주체가 서버 하나로
통일됐으므로(§3.11) FE/BE 정합 문제는 없지만, 금액 규칙인 이상 명문화는 필요하다.

### 3.8 할인 총액이 결제 금액을 넘는 경우 〔해석〕 → 최종 결제 금액 최저 0원

`couponDiscount > orderAmount + shippingFee`이면 총액을 0으로 고정한다.

### 3.9 이미 배송비가 0원인 주문의 FREESHIPPING 〔해석〕 → 적용 불가로 표시

주문 금액 10만원 이상이면 도서산간 여부와 무관하게 배송비 0원이다(§2.3 개정) →
FREESHIPPING의 할인 효과가 0이므로 "적용 가능한데 0원"이 아니라 적용 불가(비활성)로
판정한다. 0원 할인 쿠폰이 최대 2장 슬롯만 차지하는 것을 막는다.

### 3.10 판정 시계 〔해석/개정: 단순화〕 → 서버 시계 기준으로 통일

계산이 전부 서버로 이동하면서(§3.11) 시간 판정(만료일과 시간대)도 서버 시계만 쓴다.
FE는 시간을 판정하지 않는다.

- 남는 경계 사례: 화면에 "적용 가능"으로 표시된 쿠폰이 표시 이후 시간 경과로 무효가
  될 수 있다(예: 06:55에 모달을 열고 07:01에 확정). 서버가 거부하면 FE는 에러를 표시하고
  해당 쿠폰을 해제한 뒤 재계산을 요청한다.
- 〔개정 이력〕 초안의 "FE 시계로 미리보기 + BE 시계로 확정" 이중 구조는 클라 계산
  금지로 소멸. 시계가 하나가 되어 정합 문제가 사라졌다.

### 3.11 "클라이언트가 임의로 계산하지 않는다"의 적용 범위 〔해석: 신설, 핵심〕

스펙: "쿠폰을 적용하고, 결제 금액을 확인하는 과정에서 클라이언트가 임의로 계산하지 않도록
설계한다."

- 금지 대상: 금액이 결정되는 값, 곧 쿠폰별 적용 가능 여부와 할인액, 최적 조합, 주문 확인
  화면의 금액 4종(주문 금액, 할인 금액, 배송비, 최종 결제 금액). 전부 서버 계산 응답이
  SSOT다. FE는 주문서 제출과 수정으로 상품 id, 수량, `couponIds`, `isRemoteArea`만 보내고
  금액은 받기만 한다. 가격이나 금액을 요청에 싣지 않는다(서버는 DB에서 조회).
- 금지 아님: 장바구니 화면(step 2)의 합계 표시. 쿠폰이 개입하지 않는, 서버 데이터의
  순수 파생값이며 스펙의 금지 범위("쿠폰을 적용하고 결제 금액을 확인하는 과정") 밖이다.
  step 2의 클라 계산을 유지한다.
- 근거: 금지의 취지는 신뢰 경계다. 할인과 결제 금액의 원천을 클라에 두면 검증할 수 없는
  값이 화면에 뜬다. 반면 장바구니 합계까지 서버 왕복으로 만들면 수량 변경의 낙관적
  업데이트(step 2 자산)가 무력화된다. 범위를 "금액이 결정되는 과정"으로 한정하면 두
  요구를 모두 만족한다.

### 3.12 모달 토글 중의 합계 표시 〔해석/개정〕 → GET /order/coupons/preview 비저장 계산

§3.1 확정으로 정률 쿠폰의 할인액이 동반 쿠폰에 따라 달라진다. 쿠폰별 할인액의 단순
합산은 부정확하고(5,000 + 30,000 ≠ 33,500), 클라가 정액→정률 식을 실행하면 §3.11
위반이다. 그렇다고 디자인이 요구하는 버튼의 실시간 총 할인액("총 N원 할인 쿠폰 사용하기")을
포기할 수도 없다. 그래서 이 숫자는 서버가 계산해 줘야 한다.

- 초기 설계는 `GET /coupons`에 2장 이하 전 조합 할인표(최대 10개)를 동봉해 클라가 룩업하게
  했으나, 이는 전 조합 전수계산이라는 서버 내부 전략을 계약에 노출한 형태라 폐기했다(STEP3
  스펙 §5.1). 최대 적용 장수(M)가 늘면 조합 수가 가파르게 커져 응답 형태가 깨진다.
- 대신 토글 시 선택 조합을 명시적으로 묻는 `GET /order/coupons/preview?couponIds=...`로
  예상 할인을 얻는다. 저장된 주문서 기준으로 계산만 하고 저장하지 않는다. 클라 계산 없음.
- 확정 금액(금액 4종)은 여전히 "사용하기"(`PATCH /order/coupons`)와 도서산간 토글의 서버
  재계산 응답으로만 갱신한다. preview 값은 버튼 표시용이고 최종 금액 행을 직접 바꾸지 않는다.
- 근거: GET은 부수효과 없는 읽기라 메서드 의미가 동작과 일치하고, idempotent라 디바운스
  반복에 안전하다. 자체 쿼리 캐시(`shared/api/query`)가 선택 조합을 키로 캐시하면 이전 조합으로 되돌아갈 때 왕복이
  없다. 계약이 M과 무관하게 고정된다.
- 〔개정 이력〕 독립 해석 시절의 "할인액 합산 표시" → 정률 상호작용 확정으로 조합별 할인표
  룩업 → 계약 설계 검토로 preview 엔드포인트 호출. 두 번 바뀐 항목이다.

### 3.13 선택된 쿠폰의 보관 위치 〔해석/개정〕 → 서버 주문서가 SSOT (FE는 지속할 것이 없음)

적용 중인 쿠폰은 서버 주문서의 필드다. FE가 localStorage 등에 따로 지속하지 않으며,
새로고침 시 `GET /order`로 그대로 복원된다. 이때 서버가 적용 중 쿠폰을 현재 시각으로
재판정해 만료된 쿠폰을 해제하므로, 시간 종속 상태가 낡은 채 복원되는 문제도 없다.
모달 안의 임시 선택만 FE 컴포넌트 로컬 상태다(확정 전 폐기 가능해야 하므로).
